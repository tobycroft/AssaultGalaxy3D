## 一、问题现象

Debug 场景播放解体特效（爆裂 / 碎裂×10 / ×60 / ×120 / 汽化 / 黑洞 / 旋风 / 切割 / 熔陷）时，**特效出现的瞬间必然卡顿一下**。关键特征：

- **无论设定几块碎片都会卡**（×10 也卡）→ 瓶颈不在碎片数量；
- 模型面数较大。

## 二、根因分析

卡顿发生在特效**生成瞬间**（`playFx` → `extractShards`），而非逐帧运动过程。原 `extractShards` 的开销与**模型总三角形数**成正比、与档位无关，这正好解释了「无论几块都卡」：

### 2.1 海量小分配（卡顿主因）

原实现每个碎片：

- 用 `Map<number, number>` 做顶点去重；
- 用 4 个 JS `number[]` 数组（`newPos/newNor/newUv/newIdx`）`push` 顶点数据。

大模型（数十万～百万三角形）下这是**数百万次 Map 操作 + 数组 push**：JS 数组每个元素占 8 字节且伴随扩容拷贝，耗时与 GC 压力极大。且每个碎片都要把整个模型的三角形遍历一遍——**总拷贝量 = 模型全部顶点，与档位无关**。

### 2.2 每碎片重复计算矩阵

`Mat4.invert(new Mat4(), this.modelRoot.worldMatrix)` 在碎片循环内**每个碎片各算一遍**（一次分配 + 一次求逆）。

### 2.3 每次播放完整重做

预览时反复触发同一特效，切网格 + `utils.createMesh` 的显存上传**全部重来**，没有任何复用。

### 2.4 附带发现的渲染 Bug（大模型下已触发）

查证 cocos-engine 3.8.0 源码 `cocos/3d/misc/create-mesh.ts`，`utils.createMesh` 把索引格式**硬编码为 R16UI（16 位索引）**，不存在 32 位分支：

```ts
const idxStride = 2;
writeBuffer(indexBufferView, indices, Format.R16UI);
```

原代码 `indices: new Uint16Array(newIdx)` 在单组顶点数 > 65535 时索引**静默回绕**（mod 65536），碎片渲染错乱（破面/拉伸/丢失）。大模型 + 小档位时单组三角形数 ≈ 总三角形数 ÷ 档位，极易超过 21845 个三角形（×3 = 65535 顶点上限）。**即用户的模型很可能已经在错误渲染而不自知。**

## 三、优化方案

### 3.1 TypedArray 复用缓冲区 + 整表索引去重（核心修复）

| 原实现 | 新实现 |
| --- | --- |
| `Map` 去重 | `Int32Array` 整表去重（源顶点→新索引，-1 为未使用，组末 O(nv) 归还槽位） |
| JS `number[]` + `push` | 预分配 `Float32Array` / `Uint16Array` 缓冲区，**组间复用**，顺序写入 |
| `order` 用 JS 数组 | `Int32Array` |
| 索引定宽 `Uint16Array` | 见 3.3 切块后恒定 `Uint16Array` |

效果：百万次 Map/数组操作 → TypedArray 顺序读写，CPU 侧切网格耗时下降约一个数量级。

### 3.2 碎片模板缓存（按「模型 + 档位」）

关键观察：**切网格与解体模式无关**（分组只取决于档位），因此结果可缓存复用。

- 新增 `ShardTemplate { mesh; material; srcNode }` 与 `shardCache: Map<string, ShardTemplate[]>`，key = `` `${model.uuid}|${cap}` ``；
- 首次播放：切网格并缓存；**重复播放（含同档位切换模式）：直接复用网格**，跳过切网格与显存上传，仅剩节点创建；
- **矩阵不缓存**：模型会自旋（`update` 中 `currentModel.rotate(...)`），播放时用 `srcNode` 当前世界矩阵 × `modelRoot` 逆矩阵实时换算，保证碎片朝向与模型当前朝向一致；
- 切换模型时 `shardCache.clear()`，释放旧模型碎片网格显存，避免缓存悬挂与泄漏。

### 3.3 组内切块，修复 16 位索引限制

- 新增常量 `FX_MAX_TRIS_PER_SHARD = 21845`（3×21845 = 65535，恰为 R16UI 顶点上限）；
- 组内再按该上限切块，**保证每个碎片顶点数 ≤ 65535**，规避 `createMesh` 的 16 位索引回绕；
- 仅对超大组生效：常规模型每组远小于上限，行为与原实现完全一致。

### 3.4 全覆盖保证（顺带修复漏画）

原实现 `remain <= 0 → break` 会**整个跳过后续子网格/渲染器**，多子网格模型在档位用尽后的部分直接消失（特效期间模型已隐藏 → 可见破洞）。新实现 `remain = Math.max(1, shardCap - out.length)`，**档位已满时每个子网格仍至少保留 1 组**，保证全覆盖、不漏画（极端大模型下碎片数可能略超档位，以正确性优先）。

### 3.5 其它

- `modelRoot` 世界矩阵逆矩阵**每次播放只算一次**（`spawnShards` 开头，原为每碎片一次）；
- 职责拆分：`extractShards` 只负责切网格（与模式无关、可缓存、返回模板数）；新增 `spawnShards` 负责生成碎片节点 + 按模式赋予初速度/角速度/生命期（运动参数代码原样搬迁，行为不变）。

## 四、涉及文件

| 文件 | 改动 |

| `assets/Debug/Debug.ts` | 唯一改动文件。第一阶段：新增 `ShardTemplate` 接口、`FX_MAX_TRIS_PER_SHARD` 常量、`shardCache` 字段；重写 `extractShards`（模板化 + TypedArray + 切块）；新增 `spawnShards`；`playFx` 改为缓存优先；`displayModel` 切换模型时清缓存。第二阶段（读条期预缓存）：加载界面改双进度条（`createLoadingBar` / `drawLoadingBar` / `updateLoading` / `updateLoadingFx`），新增 `precacheShardTemplates`（全档位预切）与 `revealModel`（激活 + 延迟 fitModel），`loadModels` 完成后默认实例化第一个模型并走预缓存流程，加载根节点加 `BlockInputEvents` |

## 五、预期效果

1. **首次播放**：CPU 侧切网格耗时下降约一个数量级（原数百毫秒 → 几十毫秒量级）；
2. **重复播放**：仅剩约 120 个 Node + MeshRenderer 创建，切网格与显存上传全部命中缓存，卡顿基本无感；
3. **大模型 ×10 档位**：不再索引回绕错画，碎片完整；多子网格模型不再漏画。

## 六、后续可优化方向（本次未实施）

- **节点级缓存**：特效结束 `deactivate` 而非 `destroy`，重放时重置矩阵 + 重新赋予运动参数，可进一步降低重放开销（代价是常驻占显存，当前节点创建开销已可接受故未做）；
- **每帧数组压缩**：`updateFx` 中 `this.shards.filter(...)` 改为原地压缩，消除每帧新数组分配；
- **降低 draw call**：每个碎片是独立 MeshRenderer（120 档 = 120 draw call），可研究同材质碎片合批，但改动大、需引擎批处理支持；
- **读取属性开销**：`mesh.readAttribute` 对大模型有全量 CPU 拷贝，首次播放仍存在，可考虑按分组局部读取（复杂度高）；
- **全模型预缓存**：目前读条期只预缓存默认（第一个）模型，切换其他模型后首次播放该模型仍会有一次（已大幅减轻的）切网格开销，可研究空闲时后台预缓存其余模型（显存换时间，需权衡）。

## 七、第二阶段：读条期预缓存，首次播放零卡顿（2026-10-15）

### 7.1 需求

第一阶段后重复播放已无感，但**首次播放仍有几十毫秒切网格开销**。需求：把切网格前移到读条阶段，并做成**双进度条**——「模型加载」+「效果预缓存」。

### 7.2 方案

1. **读条界面改为双进度条**（`createLoading` / `createLoadingBar` / `drawLoadingBar`）
   - 原单一进度环 → 两条水平进度条：模型加载（loaded/total）+ 效果预缓存（档位 done/total），各带标签与百分比；
   - 标签左对齐用锚点 `(0, 0.5)`、百分比右对齐用锚点 `(1, 0.5)`（沿用 NewsDialog 修复过的锚点经验，避免文字偏移）；
   - 加载根节点加 `BlockInputEvents`，拦截读条期间误触（原先加载中特效按钮可点）；
   - 保留顶部旋转装饰弧与标题「正在加载…」。

2. **默认模型 + 全档位预缓存**（`precacheShardTemplates`）
   - 模型全部加载完成后，实例化**路径序第一个**模型作为默认展示（原先读条完预览区为空，需手动点按钮）；
   - 按全部档位 `[10, 60, 120]`（碎裂三档，非碎裂模式共用 `FX_MAX_SHARDS=120`，去重后三档）预切网格写入 `shardCache`——**切网格与解体模式无关，三档即覆盖全部 9 种模式**；
   - 每缓存一档 `scheduleOnce` 让出一帧重绘进度条，避免整段阻塞导致进度条不动；
   - 预缓存期间模型保持 `active=false`：已查证引擎 `Node.getComponentsInChildren` **会遍历非激活节点**（`_findChildComponents` 不判断 active），提取不受影响；碎片模板只记录来源节点，矩阵播放时实时换算，与隐藏/自旋解耦；
   - 预缓存完成 → 淡出加载界面 → `revealModel` 激活模型并延迟一帧 `fitModel`（包围盒换算需要激活后的世界矩阵）。

3. **`displayModel` 重构**：抽出 `revealModel(model)`（激活 + 延迟一帧 fitModel + 恢复自旋），按钮切换与读条亮出两条路径复用，行为不变。

### 7.3 效果

- 读条期间完成默认模型 × 3 档位的切网格与显存上传，**进入场景后首次点击任意解体特效零卡顿**；
- 切换其他模型后该模型首次播放仍有一切网格开销（已比第一阶段前轻一个量级），见 7.4。

### 7.4 已知限制

- 只预缓存默认模型：切换模型后首次播放仍有一次性开销（懒缓存），全模型预缓存会显著增加显存，未做；
- 预缓存使读条时间增加约 3 档切网格时间（大模型上数百毫秒），用第二根进度条直观展示。

## 八、读条预缓存引入的两个问题修复（2026-10-15）

预览实测发现两条控制台告警，均定位根因并修复：

### 8.1 `Can't add renderable component to this node because it already have one`

- **现象**：每次进入 Debug 场景，`bindSceneUI` 给返回按钮补背景时告警。
- **根因**：场景中 BackButton 节点已自带 `cc.Sprite`（颜色 45,74,122，与代码 `drawButtonBg` 要画的颜色完全一致），运行时又 `addComponent(Graphics)`。Cocos 一个节点只能有一个渲染组件（UIRenderer 子类互斥），添加被拒且该 Graphics 永远不会渲染——是纯死代码。
- **修复**：删除这段运行时补画逻辑，背景交由场景 Sprite 提供（视觉零变化，告警消除）。

### 8.2 `scheduler#scheduleSelector. Selector already scheduled`（严重：卡在读条页）

- **现象**：进入 Debug 场景后告警，且预缓存只推进一档（33%）就停住，加载界面不收起、页面无响应。
- **根因**：`precacheShardTemplates` 原用 `this.scheduleOnce(step, 0)` 让回调自调度。查证引擎源码：
  - `component.ts`：`scheduleOnce(cb, delay)` 就是 `schedule(cb, 0, 0, delay)`，**回调原样**传给 `Scheduler.schedule`；
  - `scheduler.ts`：`schedule` 发现同一 target 的同一 callback 已注册时，只 `logID(1507)` 告警并更新间隔、**不新建定时器**；且一次性定时器（repeat=0）在 `trigger()` 执行完回调后立即 `cancel()` 自注销。
  - 两者叠加：回调里再 scheduleOnce 同一个函数 → 告警 + 不建新定时器 → 旧定时器自注销 → **链条第一档后断裂**，`onDone` 永不执行 → 加载界面永不收起。
- **修复**：改为 **update() 驱动的任务队列**（`precacheJob` + `precacheTick`）：注册任务后由组件自身 `update` 每帧处理一档，切完自动回调。完全不涉及 scheduler，无告警、不会断链，进度条照常逐档刷新。
- **教训**：Cocos 中不要用同一函数引用的 scheduleOnce 做自调度链；逐帧任务应放 `update`，或每次传全新闭包。

### 8.3 涉及文件

`assets/Debug/Debug.ts`：删除 BackButton 的 Graphics 补画；`precacheShardTemplates` 改为注册 `precacheJob`，新增 `precacheTick` 由 `update` 每帧调用。

## 九、第三阶段：碎片缓存跨场景/跨重启固化（2026-10-15）

### 9.1 需求

第二阶段后「进入场景后首次播放」已零卡顿，但**每次进入 Debug 场景仍要重新切一遍**（大模型数百毫秒，体现在第二根进度条上）。需求：把预加载切好的碎片效果固定下来，重进场景不再重切；能接受的话重启 App 也不重切。

### 9.2 根因：原缓存天生跨不了场景

- `shardCache` 是 Debug 组件的实例字段，场景销毁即丢失；
- key 用 `model.uuid`，而模型是每次进场景 `instantiate` 的新实例——**runtime uuid 每次都不一样，跨场景必 miss**。

### 9.3 方案

1. **新增 `assets/Common/ShardStore.ts`（模块级单例，跨场景存活）**
   - key 改为 **prefab 资源 uuid + 档位**（`prefab.uuid` 稳定）；
   - 内存：直接持有 `utils.createMesh` 生成的 `Mesh` 跨场景复用（运行时创建的 Mesh 不随场景切换销毁，仅被 JS 引用持有）；
   - **来源节点不存引用、只存「模型内路径」**：模型每次进入都是新实例，旧节点已销毁；播放前由 `bindEntries` 按当前实例重新解析节点、取材质（材质实例同样不能跨场景复用）；
   - 磁盘（**仅 native**，`sys.isNative` 判定）：碎片原始数据（pos/nor/uv/idx + 节点路径）序列化到 `可写目录/shard_cache/${prefabUuid}_${cap}.bin`，二进制格式含 magic/版本/档位/碎片数/几何指纹；读取走 `getDataFromFile` 同步解析，命中即 `createMesh` 重建（只剩 GPU 上传）；`index.json` 按时间 + 容量（512MB / 30 文件）清理，顺带删散落坏文件；
   - 失效校验：**格式版本 + 几何指纹**（渲染器数 + 全部网格 AABB，`minPosition/maxPosition` 取 struct 缓存值无拷贝）——防模型重新导入后 uuid 不变但几何已变导致命中脏缓存；指纹不符/损坏的文件直接删除并回退重切；
   - 落盘用 `setTimeout(0)` 异路，不卡预缓存尾帧；失败静默（仅损失下次启动复用）。

2. **`Debug.ts` 接入**
   - `playFx` / `precacheTick` 改走 ShardStore，命中顺序：**内存 → 磁盘（native）→ 现场切割**（切完异步入盘）；
   - `extractShards` 输出改为 `ShardBlob`（原始数据，Mesh 统一由 `buildEntries` 构建），并支持 `preloaded` 预读属性：读条期对每个渲染器 `readAttribute` **只读一次、三档复用**（原实现每档全量拷贝一遍，×3）；
   - `displayModel` 切换模型**不再清缓存**（按 prefab uuid 隔离，上限 4 模型 LRU；旧模型节点销毁不影响缓存——缓存只存 Mesh + 路径）；
   - 新增 `readSubMeshes` / `modelFingerprint` / `bindEntries` 三个辅助方法。

### 9.4 效果

- **浏览器预览 / 同一次运行**：第一次进入切一次；之后 Home→Debug 反复重进，预缓存三档全部命中内存，第二根进度条瞬间走完，**零重切**；
- **native 构建**：首次切割后落盘；重启 App 再进，三档读文件重建 Mesh（仅 GPU 上传），**切割彻底跳过**；切换过的模型落盘后同样受益；
- 预缓存本身还因「读一次切三档」再快约 3 倍（省 2 遍全量 `readAttribute`）。

### 9.5 已知限制

- 浏览器预览无文件系统，刷新页面后重新切一次（内存单例救不回 JS 上下文重置）；
- 磁盘缓存只覆盖「读条期预缓存的默认模型」和「播放时现场切过并落盘的模型」；未播放过的模型重启后仍需现场切一次（与 7.4 同旨，未做全模型预缓存——显存/磁盘换时间）；
- 内存上限 4 个模型，淘汰不 destroy Mesh（特效可能正在播放；GPU 随引用释放/场景销毁回收，与既有 `clear()` 行为一致）；
- 节点路径解析依赖节点名（glb 节点名含 `/` 的极端情况会绑定失败并回退重切，理论兜底有错误提示）。

| `assets/Debug/Debug.ts` | 缓存接入 ShardStore；`ShardTemplate` 改为按实例动态绑定；`extractShards` 输出 blob + 支持预读属性；新增 `readSubMeshes`/`modelFingerprint`/`bindEntries` |
| `Doc/碎裂特效性能优化.md` | 本阶段记录 |

## 十、第四阶段：效果预加载前移至 Intro 开机预热（2026-10-15）

### 10.1 需求

Intro 开场已有模型预热（`ModelPreheater`，Prefab 进缓存）。把 Debug 里的**碎片效果预加载也前移到 Intro**：开机一次性切好，之后进 Debug 场景连读条期的第二根进度条都瞬间走完，彻底消除每次进入的切割开销。

### 10.2 架构调整：切割算法提取为共享模块

原切割逻辑全是 `Debug.ts` 私有方法，Intro 无法复用。按项目既有的 `ModelPreheater` 模式做分层：

| 文件 | 职责 |
| --- | --- |
| `assets/Common/ShardCutter.ts` | **新增**。切割算法（与模式/实例无关的纯数据操作）：`extractShards`、`readSubMeshes`、`modelFingerprint`、`nodePathWithin`/`resolveNodePath`、`FX_MAX_TRIS_PER_SHARD`。从 Debug.ts 原样搬迁，Debug 与 Intro 共用 |

### 10.3 Intro 接入

- **两段共用一个进度条**：阶段一模型预热（`preheatModels`）占前 50%，阶段二碎片预热（`ShardPreheater`）占后 50%；caption 文案随阶段切换（「星图数据同步中…」→「特效矩阵生成中…」）；绘制逻辑抽为 `drawProgress(p)`，两段各自换算总进度；
- **逐帧切档**：`Intro.update` 调 `tickShardPreheat()`（与 Debug 的 `precacheTick` 同一模式，规避 scheduleOnce 自调度链断裂问题，见 8.2）；
- **默认模型首帧异步加载**：`getDirWithPath` 的 info 只有路径没有 prefab 字段，须 `resources.load`（ModelPreheater 已预热进缓存，命中即回）；加载失败静默跳过预热，不阻塞 Intro 后续流程；
- **`onDestroy` 取消任务**：预热中途退出场景时 `cancelShardPreheat()`，防异步加载回调在场景销毁后 instantiate 出游离节点。

### 10.4 效果

| 路径 | 行为 |
| --- | --- |
| 正常启动（Intro → Home → Debug） | Intro 一次切好三档；Debug 读条期三档全命中 ShardStore，**第二根进度条瞬间 100%**，零切割 |

- Intro 只预热**默认模型**（路径序第一个）；其他模型首次播放仍懒切割（与 7.4/9.5 同旨，未做全模型预热——Intro 时长换全部模型不可取）；

- 碎片预热使 Intro 加载时长增加约 3 档切割时间（大模型数百毫秒），由进度条后 50% 展示。

## 十一、爆裂/碎裂模式去重力（2026-10-15）

### 11.1 需求

本项目是太空游戏，无重力环境。Debug 中点击爆裂（burst）/碎裂（shatter 三档）特效后，碎片会受重力向下坠落，改为**匀速四散漂移**。

### 11.2 改动

`assets/Debug/Debug.ts`：

1. **`updateFx`**：`burst` + `shatter10/60/120` 共用无重力匀速分支——不再施加 `FX_GRAVITY`，碎片沿初速度匀速直线飞出 + 自旋（打滚）；
2. **`spawnShards`**：
   - 爆裂初速度去掉 y 压扁（`dir.y * 0.7`）与上扬偏置（`+ 160 * Math.random()`）；
   - 碎裂初速度去掉 y 压扁（`dir.y * 0.5`）与上扬偏置（`+ 40`）；
   - 两项偏置都是配合重力设计的，去重力后保留会导致碎片整体向上漂而非四散；恢复为均匀球面速度 `dir * speed`，横向随机扰动与自旋保留；
3. **文案**：碎裂状态描述「塌落解体」→「四散解体」（`FX_VERBS`）；
4. `FX_GRAVITY` 保留但**仅切割（slice）模式使用**（熔陷本就用独立的 `FX_SINK_GRAVITY`），注释已标明。

### 11.3 影响面

- 爆裂、碎裂三档：匀速四散，符合太空场景；
- **切割（slice）仍有重力抛物**（两半分离后坠落），熔陷仍下沉——本次未改，如后续也想去重力按同样方式拆分支即可。

## 十二、碎裂完成度定格（2026-10-15）

### 12.1 需求

调试时需要查看碎裂「炸到一半 / 炸到八成 / 完全炸开」的形态。特效按钮栏新增**完成度按钮**：点击后直接把解体动画运行到指定完成度并**停住保持**（模型保持碎裂状态，不再继续运动、不恢复）。

档位历经两次调整：初版 50%/80%/100%；**2026-10-15 当日下午扩充为 10%/20%/30%/50%/70%/90% 六档**（更密的进度采样，便于观察炸开过程；碎裂与爆裂均适用——定格作用于当前选中的解体模式）。

### 12.2 实现

`assets/Debug/Debug.ts`：

1. **运动积分抽出 `stepShardMotion(sh, dt)`**：原 `updateFx` 内 per-shard 的 switch 分支整体迁出（位移 + 旋转，按当前模式），生命期累加/销毁/尾部缩小仍留在 `updateFx`。抽出后任意模式（含黑洞/旋风/熔陷等积分型运动）都能被小步长反复推进；
2. **`fxFrozen` 冻结字段**：`updateFx` 在引擎特效分支后判断，冻结时直接 return——碎片停住（顶部闪光不受冻结影响可自行播完），`finishFx` 不触发，模型保持隐藏；
3. **`freezeProgress(k)`**：入口。正常播放中拦截（防止误定格旧特效）；冻结中放行（重播后重新定格，状态可重复查看）；
4. **`freezeAtProgress(k)`**：逐碎片按 1/60 秒步长步进到 `k * maxLife`（最长 1.8s ≈ 108 步，一次性完成无需分帧），**不执行尾部缩小与销毁**——完成度关注的是散开形态，100% 定格即「完全炸开且完整大小」的保持状态；
5. **UI**：`EffectBar` 扩为三排（完成度按钮独立第三排，容器上移防出界）；
6. **解除冻结**：点击任意其他特效按钮（`playFx`/`playEngineFx` 门控加 `&& !fxFrozen` 放行）或切换模型（`resetFx` 清 `fxFrozen`）。

### 12.3 已知限制

- 定格中使用的是**当前选中的解体模式**（`fxMode`，即第一排最后一次点击的模式）；
- 完成度为生命期比例：50%/80% 时碎片完整大小，仅位置/旋转推进到对应进度（碎裂/爆裂为匀速，进度线性直观）；
- 冻结态会一直保持直到用户交互（无自动超时）。

## 十四、修复碎裂档位不准：单 Mesh 突破 65535 顶点上限（2026-10-15）

### 14.1 现象

用户报告：**碎裂×10 实际碎成约 70 块**（期望 10 块大碎片）。

### 14.2 根因

先用脚本分析 `resources/Model` 全部 glb：均为**单 mesh 单 primitive**（150 万三角形/78 万顶点级），排除多子网格因素。真正原因在 `extractShards` 的组内切块：

- ×10 时 `perGroup = 1500000/10 = 15万` 三角形/组；
- 但 `utils.createMesh` 把索引格式**硬编码 R16UI**（16 位，单 Mesh 顶点 ≤ 65535 = 21845 三角形，引擎 create-mesh.ts 实证），于是组内按 `FX_MAX_TRIS_PER_SHARD` 再切成 `ceil(150000/21845) = 7` 块；
- 10 组 × 7 块 = **70 块**——档位名不副实。（×60/×120 因 perGroup 小于块上限不受影响，故一直没暴露。）

### 14.3 修复

`assets/Common/ShardCutter.ts` + `assets/Common/ShardStore.ts`：

1. **新增 `buildShardMesh`**（替代 `utils.createMesh`）：复刻其打包流程（交错顶点束 + 索引束 + `Mesh.reset`），索引宽度按顶点数**自适应**——≤65535 用 R16UI，超出用 **R32UI**（32 位索引，WebGL2 原生支持；项目导入的 78 万顶点模型本就在用）。单碎片从此可容纳任意多三角形；
2. **`extractShards` 去掉组内切块**：每组即一个 Mesh；索引缓冲区（`bufIdx`）宽度随组顶点上限选 16/32 位；
3. **落盘格式升级**：`flags` 增 bit2（32 位索引标志），`CACHE_VERSION` 1→2，旧磁盘缓存自动失效重切；
4. 顶点交错写入与引擎 `writeBuffer` 布局逐字节一致（stride 32、偏移 0/12/24）；离线脚本验证分组数、布局无损、65535/65536 临界分流、45 万顶点打包 5.6ms；
5. 顺带消除 7 条既有类型错误（属性名改用 `gfx.AttributeName` 枚举、`utils.createMesh` 调用点清零）。

### 14.4 效果与代价

- ×10 = **精确 10 块**（每块约 15 万三角形），×60 = 60 块，×120 = 120 块；
- 代价：×10 档碎片变大，该档显存约从 49MB 升至 144MB（×60/×120 不变，总三角形守恒）；切割/打包耗时基本不变（打包 5.6ms/碎片量级）；
- 3.3 节的「组内切块」方案自此废弃（文档保留作历史记录）。
