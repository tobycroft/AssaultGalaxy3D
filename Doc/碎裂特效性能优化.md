---

## 一、问题现象

Debug 场景播放解体特效（爆裂 / 碎裂×10 / ×60 / ×120 / 汽化 / 黑洞 / 旋风 / 切割 / 熔陷）时，**特效出现的瞬间必然卡顿一下**。关键特征：

- **无论设定几块碎片都会卡**（×10 也卡）→ 瓶颈不在碎片数量；
- 模型面数较大。

## 二、根因分析

卡顿发生在特效**生成瞬间**（`playFx` → `extractShards`），而非逐帧运动过程。原 `extractShards` 的开销与**模型总三角形数**成正比、与档位无关，这正好解释了「无论几块都卡」：

### 2.1 海量小分配（卡顿主因）

原实现每个碎片：

- 用 `Map<number, number>` 做顶点去重；
- 用 4 个 JS `number[]` 数组（`newPos/newNor/newUv/newIdx`）`push` 顶点数据。

大模型（数十万～百万三角形）下这是**数百万次 Map 操作 + 数组 push**：JS 数组每个元素占 8 字节且伴随扩容拷贝，耗时与 GC 压力极大。且每个碎片都要把整个模型的三角形遍历一遍——**总拷贝量 = 模型全部顶点，与档位无关**。

### 2.2 每碎片重复计算矩阵

`Mat4.invert(new Mat4(), this.modelRoot.worldMatrix)` 在碎片循环内**每个碎片各算一遍**（一次分配 + 一次求逆）。

### 2.3 每次播放完整重做

预览时反复触发同一特效，切网格 + `utils.createMesh` 的显存上传**全部重来**，没有任何复用。

### 2.4 附带发现的渲染 Bug（大模型下已触发）

查证 cocos-engine 3.8.0 源码 `cocos/3d/misc/create-mesh.ts`，`utils.createMesh` 把索引格式**硬编码为 R16UI（16 位索引）**，不存在 32 位分支：

```ts
const idxStride = 2;
writeBuffer(indexBufferView, indices, Format.R16UI);
```

原代码 `indices: new Uint16Array(newIdx)` 在单组顶点数 > 65535 时索引**静默回绕**（mod 65536），碎片渲染错乱（破面/拉伸/丢失）。大模型 + 小档位时单组三角形数 ≈ 总三角形数 ÷ 档位，极易超过 21845 个三角形（×3 = 65535 顶点上限）。**即用户的模型很可能已经在错误渲染而不自知。**

## 三、优化方案

### 3.1 TypedArray 复用缓冲区 + 整表索引去重（核心修复）

| 原实现 | 新实现 |
| --- | --- |
| `Map` 去重 | `Int32Array` 整表去重（源顶点→新索引，-1 为未使用，组末 O(nv) 归还槽位） |
| JS `number[]` + `push` | 预分配 `Float32Array` / `Uint16Array` 缓冲区，**组间复用**，顺序写入 |
| `order` 用 JS 数组 | `Int32Array` |
| 索引定宽 `Uint16Array` | 见 3.3 切块后恒定 `Uint16Array` |

效果：百万次 Map/数组操作 → TypedArray 顺序读写，CPU 侧切网格耗时下降约一个数量级。

### 3.2 碎片模板缓存（按「模型 + 档位」）

关键观察：**切网格与解体模式无关**（分组只取决于档位），因此结果可缓存复用。

- 新增 `ShardTemplate { mesh; material; srcNode }` 与 `shardCache: Map<string, ShardTemplate[]>`，key = `` `${model.uuid}|${cap}` ``；
- 首次播放：切网格并缓存；**重复播放（含同档位切换模式）：直接复用网格**，跳过切网格与显存上传，仅剩节点创建；
- **矩阵不缓存**：模型会自旋（`update` 中 `currentModel.rotate(...)`），播放时用 `srcNode` 当前世界矩阵 × `modelRoot` 逆矩阵实时换算，保证碎片朝向与模型当前朝向一致；
- 切换模型时 `shardCache.clear()`，释放旧模型碎片网格显存，避免缓存悬挂与泄漏。

### 3.3 组内切块，修复 16 位索引限制

- 新增常量 `FX_MAX_TRIS_PER_SHARD = 21845`（3×21845 = 65535，恰为 R16UI 顶点上限）；
- 组内再按该上限切块，**保证每个碎片顶点数 ≤ 65535**，规避 `createMesh` 的 16 位索引回绕；
- 仅对超大组生效：常规模型每组远小于上限，行为与原实现完全一致。

### 3.4 全覆盖保证（顺带修复漏画）

原实现 `remain <= 0 → break` 会**整个跳过后续子网格/渲染器**，多子网格模型在档位用尽后的部分直接消失（特效期间模型已隐藏 → 可见破洞）。新实现 `remain = Math.max(1, shardCap - out.length)`，**档位已满时每个子网格仍至少保留 1 组**，保证全覆盖、不漏画（极端大模型下碎片数可能略超档位，以正确性优先）。

### 3.5 其它

- `modelRoot` 世界矩阵逆矩阵**每次播放只算一次**（`spawnShards` 开头，原为每碎片一次）；
- 职责拆分：`extractShards` 只负责切网格（与模式无关、可缓存、返回模板数）；新增 `spawnShards` 负责生成碎片节点 + 按模式赋予初速度/角速度/生命期（运动参数代码原样搬迁，行为不变）。

## 四、涉及文件

| 文件 | 改动 |
| --- | --- |
| `assets/Debug/Debug.ts` | 唯一改动文件。第一阶段：新增 `ShardTemplate` 接口、`FX_MAX_TRIS_PER_SHARD` 常量、`shardCache` 字段；重写 `extractShards`（模板化 + TypedArray + 切块）；新增 `spawnShards`；`playFx` 改为缓存优先；`displayModel` 切换模型时清缓存。第二阶段（读条期预缓存）：加载界面改双进度条（`createLoadingBar` / `drawLoadingBar` / `updateLoading` / `updateLoadingFx`），新增 `precacheShardTemplates`（全档位预切）与 `revealModel`（激活 + 延迟 fitModel），`loadModels` 完成后默认实例化第一个模型并走预缓存流程，加载根节点加 `BlockInputEvents` |

## 五、预期效果

1. **首次播放**：CPU 侧切网格耗时下降约一个数量级（原数百毫秒 → 几十毫秒量级）；
2. **重复播放**：仅剩约 120 个 Node + MeshRenderer 创建，切网格与显存上传全部命中缓存，卡顿基本无感；
3. **大模型 ×10 档位**：不再索引回绕错画，碎片完整；多子网格模型不再漏画。

## 六、后续可优化方向（本次未实施）

- **节点级缓存**：特效结束 `deactivate` 而非 `destroy`，重放时重置矩阵 + 重新赋予运动参数，可进一步降低重放开销（代价是常驻占显存，当前节点创建开销已可接受故未做）；
- **每帧数组压缩**：`updateFx` 中 `this.shards.filter(...)` 改为原地压缩，消除每帧新数组分配；
- **降低 draw call**：每个碎片是独立 MeshRenderer（120 档 = 120 draw call），可研究同材质碎片合批，但改动大、需引擎批处理支持；
- **读取属性开销**：`mesh.readAttribute` 对大模型有全量 CPU 拷贝，首次播放仍存在，可考虑按分组局部读取（复杂度高）；
- **全模型预缓存**：目前读条期只预缓存默认（第一个）模型，切换其他模型后首次播放该模型仍会有一次（已大幅减轻的）切网格开销，可研究空闲时后台预缓存其余模型（显存换时间，需权衡）。

## 七、第二阶段：读条期预缓存，首次播放零卡顿（2026-10-15）

### 7.1 需求

第一阶段后重复播放已无感，但**首次播放仍有几十毫秒切网格开销**。需求：把切网格前移到读条阶段，并做成**双进度条**——「模型加载」+「效果预缓存」。

### 7.2 方案

1. **读条界面改为双进度条**（`createLoading` / `createLoadingBar` / `drawLoadingBar`）
   - 原单一进度环 → 两条水平进度条：模型加载（loaded/total）+ 效果预缓存（档位 done/total），各带标签与百分比；
   - 标签左对齐用锚点 `(0, 0.5)`、百分比右对齐用锚点 `(1, 0.5)`（沿用 NewsDialog 修复过的锚点经验，避免文字偏移）；
   - 加载根节点加 `BlockInputEvents`，拦截读条期间误触（原先加载中特效按钮可点）；
   - 保留顶部旋转装饰弧与标题「正在加载…」。

2. **默认模型 + 全档位预缓存**（`precacheShardTemplates`）
   - 模型全部加载完成后，实例化**路径序第一个**模型作为默认展示（原先读条完预览区为空，需手动点按钮）；
   - 按全部档位 `[10, 60, 120]`（碎裂三档，非碎裂模式共用 `FX_MAX_SHARDS=120`，去重后三档）预切网格写入 `shardCache`——**切网格与解体模式无关，三档即覆盖全部 9 种模式**；
   - 每缓存一档 `scheduleOnce` 让出一帧重绘进度条，避免整段阻塞导致进度条不动；
   - 预缓存期间模型保持 `active=false`：已查证引擎 `Node.getComponentsInChildren` **会遍历非激活节点**（`_findChildComponents` 不判断 active），提取不受影响；碎片模板只记录来源节点，矩阵播放时实时换算，与隐藏/自旋解耦；
   - 预缓存完成 → 淡出加载界面 → `revealModel` 激活模型并延迟一帧 `fitModel`（包围盒换算需要激活后的世界矩阵）。

3. **`displayModel` 重构**：抽出 `revealModel(model)`（激活 + 延迟一帧 fitModel + 恢复自旋），按钮切换与读条亮出两条路径复用，行为不变。

### 7.3 效果

- 读条期间完成默认模型 × 3 档位的切网格与显存上传，**进入场景后首次点击任意解体特效零卡顿**；
- 切换其他模型后该模型首次播放仍有一切网格开销（已比第一阶段前轻一个量级），见 7.4。

### 7.4 已知限制

- 只预缓存默认模型：切换模型后首次播放仍有一次性开销（懒缓存），全模型预缓存会显著增加显存，未做；
- 预缓存使读条时间增加约 3 档切网格时间（大模型上数百毫秒），用第二根进度条直观展示。

## 八、读条预缓存引入的两个问题修复（2026-10-15）

预览实测发现两条控制台告警，均定位根因并修复：

### 8.1 `Can't add renderable component to this node because it already have one`

- **现象**：每次进入 Debug 场景，`bindSceneUI` 给返回按钮补背景时告警。
- **根因**：场景中 BackButton 节点已自带 `cc.Sprite`（颜色 45,74,122，与代码 `drawButtonBg` 要画的颜色完全一致），运行时又 `addComponent(Graphics)`。Cocos 一个节点只能有一个渲染组件（UIRenderer 子类互斥），添加被拒且该 Graphics 永远不会渲染——是纯死代码。
- **修复**：删除这段运行时补画逻辑，背景交由场景 Sprite 提供（视觉零变化，告警消除）。

### 8.2 `scheduler#scheduleSelector. Selector already scheduled`（严重：卡在读条页）

- **现象**：进入 Debug 场景后告警，且预缓存只推进一档（33%）就停住，加载界面不收起、页面无响应。
- **根因**：`precacheShardTemplates` 原用 `this.scheduleOnce(step, 0)` 让回调自调度。查证引擎源码：
  - `component.ts`：`scheduleOnce(cb, delay)` 就是 `schedule(cb, 0, 0, delay)`，**回调原样**传给 `Scheduler.schedule`；
  - `scheduler.ts`：`schedule` 发现同一 target 的同一 callback 已注册时，只 `logID(1507)` 告警并更新间隔、**不新建定时器**；且一次性定时器（repeat=0）在 `trigger()` 执行完回调后立即 `cancel()` 自注销。
  - 两者叠加：回调里再 scheduleOnce 同一个函数 → 告警 + 不建新定时器 → 旧定时器自注销 → **链条第一档后断裂**，`onDone` 永不执行 → 加载界面永不收起。
- **修复**：改为 **update() 驱动的任务队列**（`precacheJob` + `precacheTick`）：注册任务后由组件自身 `update` 每帧处理一档，切完自动回调。完全不涉及 scheduler，无告警、不会断链，进度条照常逐档刷新。
- **教训**：Cocos 中不要用同一函数引用的 scheduleOnce 做自调度链；逐帧任务应放 `update`，或每次传全新闭包。

### 8.3 涉及文件

`assets/Debug/Debug.ts`：删除 BackButton 的 Graphics 补画；`precacheShardTemplates` 改为注册 `precacheJob`，新增 `precacheTick` 由 `update` 每帧调用。
